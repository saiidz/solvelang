# SolveLang MCP Server v0.3.0 release candidate

_Status: candidate selection (#925), staged package finalization (#927), and Codex GitHub-marketplace import contract (#928) are repository-qualified. Full staged distribution-transition qualification is pending exact-head CI. Not tagged, not released, not published to npm, and not in the public Plugin Directory._

## Candidate intent

v0.3.0 is the selected next MCP package line for the substantial post-v0.2.0 repository work now present on `main`, including Solve Graph and Solve Context capabilities through the current candidate track.

The actually published package and canonical Codex/Claude plugin remain `@solvelang/mcp-server@0.2.0` until a separately authorized release finalization and publication succeeds. Selecting or qualifying this candidate does not authorize a GitHub Release, npm publication, marketplace/public-directory publication, provider calls, production mutation, billing, or customer-source execution.

## Staged package finalization qualification

`npm run test:release-finalization` performs a non-publishing rehearsal of the package transition while repository/public metadata remains on the actually published v0.2.0 line.

The #927 rehearsal:

1. requires the checked-in release-candidate record to remain `selected-not-published` with `publicationAuthorized: false`;
2. copies the MCP package to an isolated temporary directory;
3. changes only that temporary copy's package/lock/runtime version from v0.2.0 to v0.3.0;
4. rebuilds the temporary candidate from source using the exact installed dependency tree;
5. creates a v0.3.0 npm tarball without publication;
6. installs the tarball into a clean temporary consumer;
7. verifies the installed package and local/remote MCP runtime identify as v0.3.0; and
8. starts the installed MCP server and requires the current Solve Context tool surface.

## Full distribution transition rehearsal

`npm run test:distribution-finalization` extends the package rehearsal across the complete version-bearing plugin bundle. It operates only on an isolated temporary repository tree and never changes checked-in public metadata.

The rehearsal stages the selected candidate version across:

- `packages/mcp-server/package.json`;
- the package-lock root/package record;
- local and remote MCP runtime identity;
- Codex plugin manifest;
- Claude plugin manifest;
- canonical `.mcp.json` `npx` pin;
- Claude marketplace version metadata; and
- the Codex marketplace's reviewed local-plugin source contract.

It then runs the existing plugin-packaging validator and full plugin MCP roundtrip against that staged v0.3.0 tree. The roundtrip packs the staged MCP package, installs it into a clean consumer, starts the installed server, and exercises the reviewed tool surface. Every version-bearing distribution field must still agree on v0.3.0 afterward.

This proves the future version transition is mechanically coherent before the real repository/public version is changed. It does **not** create a tag, release, npm package, workspace import, or public-directory listing.

## Evidence boundary

Repository CI can prove deterministic behavior, package integrity, pinned-source regression results, held-out protocol mechanics, staged package/distribution finalization, and plugin/package installation boundaries. It cannot prove facts that require an independent evaluator, a managed-workspace administrator, public-directory review, or real model-provider execution.

Therefore this candidate must **not** be described as having already established:

- a genuinely blinded benchmark result;
- provider-reported token savings;
- Claude or Codex task-quality superiority;
- production latency improvement;
- a public comparative advantage over another context product;
- a completed managed-workspace marketplace import; or
- public Plugin Directory availability.

Those claims remain gated by #898, external workspace/catalog evidence, and separate publication review.

## Current evaluation truth

The visible-annotation external regression suite covers 4 repositories, 22 complete pinned source files, and 11 fixed tasks across Axios, Chalk, node-fetch, and Preact. The checked-in grading annotations are visible to implementation authors and are not a genuinely blinded benchmark.

The #924 protocol supplies machinery for a real held-out run. A genuinely blinded result still requires an independent evaluator to withhold the answer key, precommit it before selection, record the selection receipt before reveal, reveal the matching key afterward, and attest to that process.

## Publication boundary

`packages/mcp-server/release-candidate.json` remains the machine-readable source of truth for candidate selection. While it records `state: selected-not-published` and `publicationAuthorized: false`:

- `packages/mcp-server/package.json` and `package-lock.json` remain on v0.2.0;
- Codex/Claude plugin manifests and Claude marketplace metadata remain on v0.2.0;
- `plugins/solvelang/.mcp.json` continues to pin `@solvelang/mcp-server@0.2.0`;
- no v0.3.0 tag or GitHub Release should be created; and
- `.github/workflows/npm-release.yml` must remain release-published-only and protected by `npm-production`, ownership verification, exact tag/version validation, package tests, packed-consumer smoke, and Trusted Publishing.

Actual release finalization is a later reviewed change that updates the real package/lock/runtime/plugin versions coherently and passes exact-head CI before any explicitly authorized publication action.

## Rollback

Candidate-selection and qualification changes are repository tests, CI, metadata, and documentation only. Rollback is a normal reviewed revert. No production or customer data rollback is involved.
