# SolveLang MCP Server v0.3.0 release candidate

_Status: held release-ready candidate. Candidate selection (#925), staged package finalization (#927), Codex GitHub-marketplace import contract (#928), and full staged distribution transition (#929) are repository-qualified. This branch carries the real checked-in v0.3.0 package/runtime/plugin version transition for exact-head qualification. It is not merged to `main`, not tagged, not released, not published to npm, and not listed in the public Plugin Directory._

## Release-ready intent

v0.3.0 is the selected next MCP package line for the substantial post-v0.2.0 Solve Graph and Solve Context work present on current `main`.

The actually published package remains `@solvelang/mcp-server@0.2.0`. This held branch intentionally carries v0.3.0 metadata only so the exact release commit can be tested before publication. `packages/mcp-server/release-candidate.json` records `state: release-ready-not-published` and `publicationAuthorized: false`.

Do not merge this branch into `main` unless the release sequence is explicitly authorized and ready to publish immediately. Merging it without publication would make the canonical plugin pin reference an unpublished package.

## Qualification gates

The release-ready branch keeps all prior release gates and adds no alternate publish path.

The live `Protect main` ruleset is active with no bypass actors, requires pull requests and resolved review conversations, requires branches to be up to date, blocks deletion and non-fast-forward updates, and requires these four GitHub Actions checks: `Rust runtime`, `Static site`, `SolveLang Rust security and tests`, and `WASM artifact security`.

`npm run test:release-candidate` validates the selected vs release-ready state, exact package/plugin version agreement, and the fail-closed npm release workflow.

`npm run test:release-finalization` builds and packs the current v0.3.0 package, installs it into a clean temporary consumer, verifies local/remote runtime identity, starts the installed MCP server, and requires the current Solve Context tool surface.

`npm run test:distribution-finalization` copies the full v0.3.0 distribution bundle to an isolated temporary tree, validates package/plugin/marketplace consistency, packs and clean-installs the package, starts the installed server, and runs the real plugin MCP roundtrip. Every version-bearing field must remain v0.3.0 after the roundtrip.

The standard MCP CI, dependency audit, held-out protocol mechanics, general CI, Rust/security, WASM artifact security, and Launch Readiness checks remain applicable.

## Publication boundary

Publication is still a separate action. This branch does **not** authorize or perform:

- a v0.3.0 Git tag;
- a GitHub Release;
- npm publication;
- a managed-workspace marketplace import;
- public Plugin Directory publication/review;
- provider/model calls;
- production mutation;
- billing or customer-source execution.

`.github/workflows/npm-release.yml` remains release-published-only and must stay protected by `NPM_SCOPE_OWNERSHIP_VERIFIED`, the `npm-production` environment, exact tag/version validation, package tests, packed-consumer smoke, and npm Trusted Publishing.

## Evidence boundary

Repository qualification does not establish a genuinely blinded benchmark, provider-reported token savings, Claude/Codex superiority, production latency improvement, or public comparative advantage. Those claims remain gated by #898's real-evidence matrix and separate publication review.

The visible-annotation external regression suite still covers 4 repositories, 22 complete pinned source files, and 11 fixed tasks across Axios, Chalk, node-fetch, and Preact. The #924 held-out protocol machinery exists, but a genuinely independent execution still requires an external evaluator/process.

## Release sequence

1. Qualify this exact held v0.3.0 head through all applicable PR checks and review state.
2. Confirm the live GitHub `main` protection ruleset and npm production/ownership controls.
3. Receive explicit release/publication authorization.
4. Merge the exact qualified head to `main` without unrelated changes.
5. Create/publish the exact `v0.3.0` GitHub Release so the protected npm workflow publishes the matching package.
6. Verify npm package availability before treating the canonical v0.3.0 plugin pin as usable.
7. Verify managed-workspace installation, then separately pursue public Plugin Directory publication/review.

## Rollback

Before publication, rollback is simply closing or reverting the held release branch. After publication, package immutability means rollback should use a new corrective version rather than rewriting v0.3.0. Production/customer state is not mutated by this release branch.
